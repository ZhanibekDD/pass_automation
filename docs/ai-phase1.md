# Pass Docs AI — phase 1

## Границы этапа

В репозитории отсутствует Django-система, поэтому этот этап не создаёт
фиктивные Django-модели и не пытается угадать production-схему. Он добавляет
локальный sidecar и узкий read-only адаптер к существующему JSON.

Изменения существующего ASDPO-пайплайна ограничены `.gitignore`; код генерации
Excel, ZIP, структура файлов и SMTP не изменены.

## Поток данных

1. Адаптер читает `package_input.json` через существующий `input_loader`.
2. Файл проверяется по размеру и формату, PDF рендерится постранично.
3. Одна страница отправляется только локальной Ollama/vLLM vision-модели.
4. Ответ проверяется строгой Pydantic-схемой.
5. Все поля, включая `null`, сохраняются с employee/document ID, confidence,
   source file и page.
6. Детерминированные правила создают findings.
7. Findings попадают в ручную очередь.
8. Подтверждение/отклонение оператора и AI-запуски фиксируются в audit log.

## Таблицы локальной SQLite

- `ai_runs` — запуск и ошибка без сырого ответа модели;
- `ai_extractions` — найденные значения и provenance;
- `ai_findings` — нарушения и дедупликационный ключ;
- `ai_review_queue` — ручной статус, оператор и комментарий;
- `ai_document_fingerprints` — SHA-256 для поиска дублей;
- `ai_audit_log` — действия AI, системы и оператора.

Схема создаётся идемпотентно при старте API/CLI и имеет
`PRAGMA user_version = 1`.

## Реализованные проверки

- обязательные коды отсутствуют;
- дата окончания меньше текущей даты;
- на датируемом документе не найдено ни одной даты;
- нормализованное ФИО не совпадает;
- нормализованный ИИН не совпадает;
- одинаковый SHA-256 используется в другом документе;
- совпали оба признака чужого сотрудника — ФИО и ИИН;
- низкая уверенность любого непустого поля.

«Документ другого сотрудника» также определяется по fingerprint, если один и
тот же файл уже зарегистрирован с другим `employee_id`.

## Защита от выдуманных данных

- temperature равна нулю;
- prompt требует `null`, когда значение не видно;
- JSON schema запрещает дополнительные поля;
- confidence валидируется в диапазоне 0–1;
- сырой свободный текст модели не принимается;
- отсутствие даты хранится как JSON `null`, а не как придуманная дата;
- бизнес-правила выполняются вне LLM.

Это снижает риск, но не делает vision безошибочным. Любое расхождение и низкая
уверенность требуют ручного решения.

## Следующий этап интеграции с Django

После добавления фактического Django-кода:

1. реализовать адаптер к реальным `Employee`/`Document` только на чтение;
2. заменить составной `document_id` на реальный PK/UUID;
3. добавить outbox-задачу после загрузки документа;
4. перенести фоновые запуски в существующую Celery/RQ-систему;
5. добавить permissions из Django и корпоративный SSO;
6. хранить локальную AI-схему в отдельной БД или отдельном namespace;
7. добавить Nginx location без публичного доступа;
8. провести тест на размеченном наборе без персональных данных.

## Риски и эксплуатационные метрики

- Vision-модель: измерять field accuracy и false-positive rate по типам
  документов.
- Очередь: контролировать pending count и median review time.
- Инфраструктура: следить за model availability, failed runs и latency/page.
- Приватность: не логировать изображения, prompt и сырой ответ модели.
- Производительность: лимиты 20 МБ, 20 страниц и 2200 px на страницу меняются
  через env.

Первый критерий допуска к production: на обезличенном контрольном наборе
критические ошибки («чужой документ», ИИН, срок действия) должны иметь
предварительно согласованный recall, а все неподтверждённые результаты должны
оставаться в ручной очереди.
